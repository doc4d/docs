Roles y privilegios

La arquitectura de seguridad ORDA controla el acceso a los recursos del proyecto para las sesiones web y REST. Le permite conceder permisos específicos sobre recursos tales como el datastore, las bases de datos, los atributos y las funciones.

Generalidades​

El modelo de seguridad combina privileges, actions (como read y create), y resources.

Asigne privilegios a una session utilizando Session.setPrivileges().

Cada solicitud se verifica con los permisos definidos en el archivo roles.json del proyecto. Una acción no autorizada genera un error de privilegios. Los atributos sin permiso de lectura se omiten en la respuesta.

Entradas de blog relacionadas

Filtre el acceso a sus datos con un sistema completo de permisos**

info

Los permisos controlan el acceso a los objetos o funciones del almacén de datos. Si desea filtrar los datos leídos según algún criterio, puede considerar restringir las selecciones de entidades que puede ser más apropiado en este caso.

Alcance​

Los permisos se aplican a las sesiones web y REST: solicitudes REST, incluidas las páginas Qodly, las sesiones de Open datastore, las sesiones MCP y el código 4D ejecutado en un proceso web. Esto incluye las funciones expuestas, los gestores de solicitudes HTTP, el método base On Web Connection y cualquier código al que estos hagan referencia. Por ejemplo, una llamada a una función permitida seguirá fallando si la función lee una clase de datos para la que la sesión no tiene permiso de lectura.

Excepción

El permiso execute de un singleton compartido o una función singleton solo se verifica cuando la función se invoca a través de REST. Cuando el código 4D se ejecuta en una sesión web lo llama directamente (cs.MySingleton.me.myFunction()), no se comprueba ningún permiso, a diferencia de las funciones de dataclass, entidades, selección de entidades y de datastores que se verifican en ambos casos.

Los permisos nunca se aplican al código de sesión de escritorio (autónomo, cliente/servidor, procedimientos almacenados) ni a tool4d.

atención

Cuando una entrada de permiso hace referencia a un privilegio no declarado, 4D registra un error e ignora la entrada. En este caso, el permiso se ignora. Si el modo restringido por defecto no está habilitado, el recurso es accesible a las sesiones guest.

4D verifica los permisos de la sesión cada vez que se accede a un recurso. Los siguientes recursos pueden tener permisos específicos:

Utilice los valores applyTo y type que se muestran en la tabla a la hora de definir los permisos en roles.json.

Asignación de permisos a las funciones de la clase ORDA

En roles.json, identifique una función de clase ORDA en applyTo con esta sintaxis:

<DataclassName>.<functionName>

Por ejemplo, si desea aplicar un permiso a la siguiente función:

// cs.CityEntity class
Class extends Entity
  Function getPopulation() : Integer
   ...

Utilice este valor:

"applyTo":"City.getPopulation"

Dado que los permisos identifican las funciones por dataclass y nombre de función, no es posible asignar privilegios diferentes a funciones con el mismo nombre que pertenezcan a clases ORDA distintas (entidad, entity selection, dataclass). En su lugar, déles nombres distintos. Por ejemplo, asigne a las funciones los nombres dropEntity() y dropSelection() en cs.CityEntity y cs.CitySelection, respectivamente:

	"permissions": {
		"allowed": [
			{
				"applyTo": "City.dropEntity",
				"type": "method",
				"execute": [
					"cityAdmin"
				],
				"promote": [
					"name"
				]
			},
			{
				"applyTo": "City.dropSelection",
				"type": "method",
				"promote": [
					"name"
				]
			}
		]
	}
}

Permisos​

Un permiso permite realizar una acción sobre un recurso; por ejemplo, ejecutar ds.myTable.myFunction(). Los permisos se definen en roles.json y se conceden a uno o varios privilegios.

Si no se ha definido ningún permiso para un recurso, el acceso depende del modo de restricción del proyecto.

Acciones de autorización​

Las acciones disponibles dependen del recurso:

AcciónDatastoreDataclassAtributoFunction
createCrear entidades en cualquier dataclassCrear entidades en este dataclassCrea una entidad con un valor distinto del predeterminado para este atributo (se ignora en el caso de los atributos alias)n/a
readLeer atributos en cualquier dataclassLeer atributos en esta clase de datosLee el contenido de este atributon/a
updateActualizar atributos en cualquier clase de datosActualiza los atributos de esta clase de datosActualiza el contenido de este atributo (se ignora en el caso de los atributos alias)n/a
drop ("Delete" en Qodly Studio)Borrar datos en cualquier clase de datosBorrar los datos de esta clase de datosEliminar un valor distinto de nulo para este atributo (excepto alias y atributos calculados)n/a
executeEjecutar toda función en el proyecto (datastore, dataclass, entity selection, entidad, singleton)Ejecuta cualquier función en la dataclass; las funciones de dataclass, de entidades y de entity selection se tratan como funciones de dataclassn/aEjecutar esta función
promoten/an/an/aAñadir temporalmente un privilegio mientras dure la llamada a la función. Solo el proceso que ejecuta la función la recibe, no toda la sesión. Utilice promote() y demote() para definir o eliminar esta acción de dinámicamente en un proceso web.

Reglas de permisos​

  • update y drop requieren read sobre el recurso; create no lo requiere.
  • Una función puede ser promoted con múltiples privilegios. Durante la ejecución, recibe los permisos combinados de todos esos privilegios; no existe un orden de prioridad.
  • Un atributo alias se puede leer si la sesión tiene permiso para leer el alias, aunque no pueda leer los atributos a los que resuelve el alias.
  • Se puede acceder a un atributo calculado incluso si sus atributos subyacentes no tienen permisos.
  • En modo de inicio de sesión forzado de REST, los usuarios invitados siempre pueden ejecutar authentify(), independientemente de la configuración de permisos.

Permisos heredados​

Las acciones de permisos se heredan según las siguientes reglas:

  1. Permisos descienden datastore → dataclass → atributo / función y datastore → singleton → función singleton.
  2. La resolución es por acción. Definir read en un dataclass no cambia cómo create, update, drop o execute son resueltos para ella.
  3. La dataclass sustituye al datastore. Un permiso definido en un dataclass para una acción reemplaza la autorización del datastore para esa acción. Los privilegios concedidos a la acción únicamente en el datastore se pierden en esa dataclass.
  4. La función reemplaza la dataclass. Un permiso execute definido en una función reemplaza el permiso execute para esta función en la dataclass (y el datastore). Las funciones de entidad y de selección de entidades siguen la misma regla que las funciones de dataclass.
  5. El singleton reeemplaza al datastore, la función singleton reeemplaza al singleton.
  6. La función Datastore reemplaza al datastore.
  7. Una función hereda lo que no define. En todos los niveles, una acción que el permiso de una función no muestra es heredada de su dataclass o singleton, luego del datastore. Por ejemplo, un permiso de función singleton que solo define a promote mantiene el permiso execute de su singleton. A promote permission never grants execute: to let a privilege call a promoted function, list it in the function's execute permission.
  8. Attribute adds to its parent. To act on an attribute that has its own permission, a session needs a privilege granted by the attribute permission and a privilege granted the action on the dataclass (directly or through the datastore).
  9. An action granted to no privilege (for example, "read": []) is "not set", so the permission at the level above applies. It does not mean "nobody". To deny the action, use restricted mode without defining that permission, or grant it to a privilege that no session receives.

Permissions only grant access; there is no explicit deny. A dataclass or function permission can therefore narrow a broader datastore permission by replacing it. An attribute permission is additive: it grants access to that attribute only when the session also has the action on its dataclass.

Práctica recomendada
  • Assign access to sessions through roles with Session.setPrivileges({roles: [...]}). Define roles around business profiles; privileges are the reusable building blocks. Qodly Studio displays effective permissions by role.
  • If an administration role needs full access, include every privilege in it except a lock privilege, if used. Add each new privilege to that role: a dataclass-level permission can replace a broader datastore permission.
  • Review the effect of privilege changes on every role. In Qodly Studio, Detailed Permission Review shows a role's effective access; a role with no privileges can help you review guest-only access.

Privilegios y roles​

A privilege grants actions on resources. A role groups privileges into a business profile that an administrator can assign to a session.

For example, manageInvoices could be a privilege and secretary a role that includes it and other privileges. Assign roles to sessions with Session.setPrivileges({roles: [...]}); the role grants all its privileges.

Privileges can be granted permission on multiple action-resource combinations, and an action can be granted to multiple privileges.

Define privileges and roles in roles.json, then grant roles to sessions with Session.setPrivileges().

Privilegios incluidos​

A privilege can include other privileges using the includes property in roles.json. Inclusion is transitive and one-way: if A includes B, and B includes C, A receives the permissions of B and C.

Session.getPrivileges() returns the expanded collection (for example, A, B, and C) in no guaranteed order. Declare an included privilege before the privilege that includes it; otherwise, 4D drops the inclusion and logs an error.

Ejemplo​

This authentication function assigns the user's role to the session:

exposed Function authenticate($identifier : Text; $password : Text)->$result : Text

    var $user : cs.UsersEntity

    Session.clearPrivileges()

    $result:="You are authenticated as Guest"

    $user:=ds.Users.query("identifier = :1"; $identifier).first()

    If ($user#Null)
        If (Verify password hash($password; $user.password))
            Session.setPrivileges(New object("roles"; $user.role))
            $result:="Your are authenticated as "+$user.role
        End if
    End if


Privilegio guest​

guest is built in; declaring a privilege named Guest is an error ("privilege already defined"). Sessions without privileges (Session.isGuest() = True) receive the permissions granted to guest.

Permissions granted to guest are available to every session, regardless of its other privileges. Do not grant guest access that should be withheld from other sessions, and account for its permissions when restricting access at the dataclass level.

Archivo roles.json​

The project's web security settings are defined in roles.json:

permissions.allowed[].applyToTextSíTarget resource name.
permissions.allowed[].typeTextSíResource type: datastore, dataclass, attribute, method, singletonMethod, or singleton.

permissions.allowed[].createColección de cadenasNoPrivileges granted create access.
permissions.allowed[].updateColección de cadenasNoPrivileges granted update access.
permissions.allowed[].dropColección de cadenasNoPrivileges granted delete access.
permissions.allowed[].executeColección de cadenasNoPrivileges granted execute access.

Notas
  • The WebAdmin privilege name is reserved for the application; do not use it for custom privileges.
  • Privilege and role names are case-insensitive. Unknown names passed to .setPrivileges() are ignored.
  • Qodly Studio can add an optional id property to privileges and roles to preserve references when they are renamed.
  • Multiple entries with the same applyTo are not merged: the last entry wins without an error. Define only one entry per resource.
  • A resource entry that grants no actions has no effect.
atención

Cuando una entrada de permiso hace referencia a un privilegio no declarado, 4D registra un error e ignora la entrada. En este caso, el permiso se ignora. Si el modo restringido por defecto no está habilitado, el recurso es accesible a las sesiones guest.

Compatibilidad

En las versiones anteriores a la 4D 20 R6, el archivo roles.json no se creaba de forma predeterminada. In 4D 20 R6 and later, opening an existing project without a roles.json file or "forceLogin": true setting makes the Activate REST authentication through ds.authentify() function button available on the Web Features page of the Settings dialog box. This button upgrades the security settings; you may need to modify your code. Ver esta entrada del blog.

Qodly Studio

En Qodly Studio for 4D, el modo de conexión se puede definir utilizando la opción Forzar inicio de sesión en el panel Roles y privilegios.

Modos de restricción​

restrictedByDefault determines access to a resource when no specific permission is defined:

  • Unrestricted mode (restrictedByDefault: false): Resources without defined permissions are accessible to all requests.
  • Restricted mode (restrictedByDefault: true): Resources without defined permissions are blocked. Access is granted explicitly, and the permission inheritance rules still apply.
Compatibilidad
  • New projects set restrictedByDefault to false by default; see recommended configurations.
  • For projects converted from earlier releases, enabling access to Qodly Studio through the One-click configuration dialog adds restrictedByDefault: true to roles.json.

Estrategias de restricción​

Lock everything and open gradually​

Choose either restricted mode or a lock privilege to close access by default:

Modo restringidoLock privilege
Setting"restrictedByDefault": true (Qodly Studio: Restrict Access By Default)"restrictedByDefault": false, with every action on ds granted to a privilege that no session receives (for example, none)
What is closedEvery resource without a permissionEvery resource that inherits datastore permissions
How to openGrant permissions on the datastore, dataclasses, attributes, and functionsGrant permissions on dataclasses and functions to replace the lock
If 4D drops an invalid entryThe resource stays closedThe resource falls back to the lock and stays closed
ImportanteExplicitly grant access to public resources, usually to guest, including the login function unless force login is used, and HTTP request handlers called before login. In this mode, Qodly Studio's role review is currently incorrect.Never assign the lock privilege to a role, including the administration role.

Both approaches close access by default and follow the same inheritance and replacement rules. A lock privilege makes the lock visible in the editor; restricted mode requires no extra privilege.

Open everything, restrict gradually​

Set unrestricted mode ("restrictedByDefault": false), grant guest read access to ds, then restrict sensitive dataclasses with dataclass-level permissions.

Remember that guest permissions apply to every session. Without a lock privilege, an invalid entry dropped by 4D leaves the resource open in unrestricted mode.

Configuración recomendada​

Use these settings as a starting point:

  • Development: Set both properties to false for easier access while developing and debugging. Apply restrictions gradually as needed.
  • Production: Set restrictedByDefault and forceLogin to true so that users must authenticate and resource access must be explicitly granted.

Errores de permisos​

Archivo Roles_Errors.json​

4D parses roles.json at startup. Restart the application for changes to take effect.

If parsing fails, 4D writes the errors to Roles_Errors.json in the project's Logs folder. It deletes this file after roles.json is corrected.

Check at startup, especially in production, whether Roles_Errors.json exists. Its presence indicates a parsing error, and permissions may not be enforced as intended. Puede escribir, por ejemplo:

/Sources/DatabaseMethods/onStartup.4dm
If (Not(File("/LOGS/"+"Roles_Errors.json").exists))
...
Else // you can prevent the project to open
 ALERT("The roles.json file is malformed or contains inconsistencies, the application will quit.")
 QUIT 4D
End if

Los errores de permisos se muestran de la siguiente manera:

Rutaread / create / update / drop refusedexecute refused
RESTHTTP 401 with messageHTTP 500 with message (singleton: "Bad permission...")
Código (sesión web)Read: error 1557 (dataclass) or 1607 (attribute). Create: error 1608 when assigning an attribute to a new entity if create is restricted by a permission; in restricted mode without permission, save() returns success: false and statusText: "Permission Error". Update/drop: error 1557 when loading the entity (both require read).Error 1561

Ejemplo​

This example grants a broad set of permissions through a manager privilege, while the payroll privilege grants read access to the sensitive Salaries dataclass.

roles.json
{
  "forceLogin": true,
  "restrictedByDefault": true,
  "privileges": [
    {"privilege": "payroll", "includes": []},
    {"privilege": "manager", "includes": []}
  ],
  "roles": [
    {"role": "administrator", "privileges": ["manager", "payroll"]}
  ],
  "permissions": {
    "allowed": [
      {
        "applyTo": "ds",
        "type": "datastore",
        "read": ["manager"],
        "create": ["manager"],
        "update": ["manager"],
        "drop": ["manager"],
        "execute": ["manager"]
      },
      {
        "applyTo": "Salaries",
        "type": "dataclass",
        "read": ["payroll"]
      }
    ]
  }
}

Estas son las reglas resultantes:

SessionRead SalariesCreate SalariesUpdate/drop SalariesRead other dataclasses
managerRefused (the Salaries read permission replaces the datastore permission)Allowed (inherited from the datastore)Refused (read is required)Allowed
payrollAllowedRefused (the datastore permission is granted only to manager)RefusedRefused
rol de administradorAllowedAllowedAllowedAllowed

The Salaries read permission replaces the datastore read permission, so manager alone cannot read that dataclass. The administrator role receives the combined permissions of manager and payroll.
